Publishing tonto ontologies

A published tonto ontology is its source folder, put on the web where other models can import it, with the OWL beside it. There is no export step for the source: the .tonto files you check are the files you publish. This guide follows one ontology, shop, from a folder on disk to a verified release that depends on another ontology somebody else publishes.

1What one ontology is

An ontology is the unit that is published: one namespace, one Turtle file, one version. Every class name is a public identifier of its ontology, so within one ontology a name is declared once, whichever package declares it. A use decides what a package can see; it never separates identities.

These words are used everywhere, in this guide, the diagnostics and the editor, each for one thing:

A file says what it is in its first line:

One file

ontology shop, then declarations

A one-file ontology: the declarations after the header are the whole ontology. This is how the starter model begins, and needs no package.

Packages

ontology shop bundles …

An ontology file with packages: written under the header, or bundled from package files of their own. Each package file starts package core in shop, and it and the ontology file must agree.

No header

package … and no ontology

An error: every package belongs to an ontology a document declares. The repairs make it a one-file ontology, write a header above it, or bundle it into an existing ontology file. A folder, a shared namespace or a tonto.json never makes one.

2Name the ontology and its packages

Most ontologies begin as one file: ontology shop followed by its declarations. When it outgrows the file, run tonto: New Package…, or put the cursor on the ontology line and choose Split “shop” into an ontology file and package “core”. Either way the declarations move to core.tonto, which starts package core in shop, and the header stays where it was, with its documentation and namespace: shop.tonto is still the ontology file. No IRI changes. New Package… then writes the new package’s file and its bundle entry, together, and does the same for every package after it.

An ontology file with bundles names the packages the ontology bundles and the file each one is in, and its documentation carries the ontology’s metadata. The namespace is the ontology’s public identity: a hash namespace (ending in #) is required for publication. The packages it bundles carry no namespace of their own; they publish into the ontology’s.

{{SHOP_FILES}}

What to notice

  • Each bundle entry is a package name and the location of the file that declares it, relative to the ontology file. The package files stay where they are.
  • Each package file says which ontology it belongs to: package sales in shop. Publication refuses a bundled package that does not say so, and a package that says so but is not bundled.
  • Ontology names, package names and import aliases are lowercase.
  • sales refers to catalog with use catalog, because both belong to shop. import catalog would be an error, with a fix that rewrites it: packages are used, ontologies imported.
  • sales imports people by location, because it belongs to someone else. The alias people qualifies its names: people.Person.

3Import another ontology by location

The people ontology is published at https://example.org/people/people.tonto. Its importer names that location; it never names a package that lives in another ontology. A use across that boundary is refused with cross-ontology-package-use, which says which location import to write instead. The location is always an ontology’s ontology file, never one of its package files.

Checking never touches the network. Until the document is on this machine, the import is reported, and the ontology that imports it is checked only for names and ownership, so nothing is reported as though people were absent:

{{PEOPLE}}{{UNMAPPED}}

4Develop against a local copy

While both ontologies are being developed, point the published location at a local folder. A mapping substitutes the source of a document without changing the import that names it, so the model keeps saying what it will say once published.

{{MAPPING}}{{MAPPED}}
  • A key ending in / maps every location beneath it, and its value must end in / as well. The longest matching key wins.
  • A relative value is resolved against the folder holding tonto.json. Here ../people/ is a sibling checkout.
  • A local target inside the workspace is checked like your own files; one outside it is read-only.
  • Only your own tonto.json is read. A dependency’s tonto.json is never consulted.
  • A malformed file or entry is reported on the workspace’s first file, and the valid entries beside it still apply. --locations='{…}' supplies the same mappings on the command line.

5Verify the release without mappings

A release must check against what its importers will actually read: the published documents. --publication switches every mapping off, so the local copy no longer stands in. tonto fetch --publication is the only command that goes to the network. It retrieves the whole dependency closure into {{CACHE}} in one step, and checking then reads it from there, offline:

{{VERIFY}}

The cache records, for each document, where it was requested, where it was actually fetched from after redirects, when, and a SHA-256 digest of its content. A cached document does not change until you ask for a refresh. Development and publication keep separate caches. The cache is local state: keep .tonto/ out of version control and out of the published folder.

6Export the gUFO Turtle

Every export of an ontology is written beside its ontology file, named after the ontology. The gUFO export is one Turtle file per ontology, here shop.ttl beside shop.tonto. --publication exports only after the same unmapped verification succeeds. The dependency stays where it is: shop refers to people:Person by its own IRI and imports its ontology, and nothing of people is copied into shop.

{{EXPORT}}{{TURTLE}}

7Put the folder on the web

Publish the source files at the locations their importers will use, keeping their relative layout, since the ontology file names its packages by relative location. The Turtle is already beside the ontology file, so the folder goes up as it is. For shop on https://example.org/:

AddressServeRead by
https://example.org/shop/shop.tontoshop.tontotonto models that import shop from <…/shop.tonto>
https://example.org/shop/catalog/products.tontocatalog/products.tontotonto, following the ontology file
https://example.org/shop/sales/orders.tontosales/orders.tontotonto, following the ontology file
https://example.org/shop/shop.ttlshop.ttlPeople and tools that want the OWL
https://example.org/shopthe Turtle, or a redirect to shop.ttlRDF tools following owl:imports

The last row is the ontology IRI: the namespace without its #. It names the ontology, not a file, and RDF tools that follow owl:imports <https://example.org/shop> expect Turtle there.

  • A host that serves extensionless files with a configurable content type (S3, for example) can serve the Turtle at the ontology IRI directly, with Content-Type: text/turtle.
  • A host that serves a folder of files cannot have both a file shop and a folder shop/. Configure a redirect from the ontology IRI to the .ttl instead: on the host, or through a persistent-identifier service such as w3id.org or a PURL server. A persistent identifier also lets the files move later without changing the IRI.
  • No content negotiation is needed. tonto importers name the .tonto location; RDF clients ask for the ontology IRI.
  • Do not rewrite locations while copying. If the files must move, keep their relative layout, or update the locations in the source and check again.

Once published, a location is an address other models depend on. Changing the namespace changes every IRI in the ontology; changing a document’s location breaks every import that names it. Publish a new release at a new location, and leave the old one where it is.

8Follow a dependency that changes

When people publishes a change, nothing happens on your side until you ask for it. A refresh retrieves the closure again, all of it or none of it, and says which documents changed, which are new, and which are no longer needed:

{{REFRESH}}

A fetch over the whole workspace also drops documents that no import needs any more. A fetch of some files keeps them, since other files may still need them. If a refresh fails part way, the previous documents stay in use.
